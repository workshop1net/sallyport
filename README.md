# Sallyport

A small, self-hosted gateway for giving third parties (an MSP's engineers, a vendor's support staff) remote access to systems **without a VPN and without exposing RDP or SSH**.

> *sallyport*: a controlled gateway in a fortification, from which defenders can go out and through which others are admitted.

**Status: MVP, untested end to end.** Read [Known limitations](#known-limitations-mvp) before using it for anything real.

## How it works

```
 engineer's browser
        |  HTTPS (443/80)           the only thing exposed to the internet
        v
   +----------+   OIDC    +--------------------+
   | Pomerium |<--------->| your IdP (Entra,   |   phishing-resistant MFA is
   | (Envoy)  |           | Okta, Google, ...) |   enforced here
   +----+-----+           +--------------------+
        | identity header, internal network only
        v
   +-----------+     +-----------+
   | Guacamole |---->|  guacd    |-----> RDP / SSH to target systems
   | web app   |     +-----------+
   +-----+-----+
         v
   +-----------+
   | Postgres  |  connections, accounts
   +-----------+
```

The engineer only ever receives pixels. Their device never speaks RDP or SSH to your network, so malware on it cannot tunnel in, and there is no VPN to hand out. Pomerium decides who may reach Guacamole, and Guacamole decides which targets they see. Guacamole trusts the identity header Pomerium sets and checks nothing itself, so **Guacamole must never be reachable except through Pomerium**. The Compose file enforces this with an `internal: true` network.

## Requirements

- A Linux server with Docker and the Compose plugin. Roughly 2 vCPU, 4 GB RAM and 40 GB disk is a reasonable starting point for one concurrent session (an estimate, not a benchmark).
- For the helper script: Python 3 with PyYAML (`apt install python3-yaml`), or on Windows, nothing extra (see below).
- DNS names for `<domain>` and `authenticate.<domain>` pointing at the server, with ports 80 and 443 open to the internet (Let's Encrypt).
- An OpenID Connect identity provider that can emit group IDs if you want group-based access.

## Quick start

```sh
cp sallyport.example.yaml sallyport.yaml   # edit: domain, IdP, who is allowed in
chmod 600 sallyport.yaml

./sallyport init            # secrets, generated config, database schema
docker compose up -d --build
./sallyport migrate-db      # creates the admin tables (re-run after upgrades; harmless)
```

Add `admin.emails` to `sallyport.yaml` (or use the control panel), point DNS for `admin.<domain>` at the server as well, then open `https://admin.<domain>` to add systems, people and logins.

Register `https://authenticate.<domain>/oauth2/callback` as the redirect URI with your IdP. Start with `acme_staging: true`; once Pomerium obtains a staging certificate, set it to `false`, re-run `./sallyport init` and `docker compose up -d`.

You never edit `compose.yaml`. Operators change `sallyport.yaml`; targets are managed in the admin site.

## Dev mode (local testing)

To test the installer and the whole stack without Let's Encrypt or a real IdP:

```sh
cp sallyport.dev.example.yaml sallyport.yaml   # mode: dev, domain: access.localhost
./sallyport init                               # (sallyport.cmd init on Windows)
docker compose -f compose.yaml -f compose.dev.yaml up -d
./sallyport migrate-db                         # creates the admin tables and loads the test targets
```

Then open `https://access.localhost` and accept the certificate warning (browsers send `*.localhost` to your own machine, so no DNS is needed). If the sign-in redirect fails, open `https://dex.access.localhost:5556` once and accept its warning as well. Dev mode's identity provider is Dex with a password login. Sign in as `kilgore@kilgore.trout` (the administrator, who can also open `https://admin.access.localhost`), or as `billy.pilgrim@`, `eliot.rosewater@` or `montana.wildhack@kilgore.trout`; the password is `password` for all four. To switch identity, sign out or use a private window, so you can test several people against the same logins. The `sshtest` target opens a shell in a throwaway SSH container. A second target, `rdptest`, is a throwaway xrdp desktop (login `abc` / `abc`) for trying RDP settings. It uses `security: tls` and `ignore_cert: true` because xrdp does not support NLA, so NLA stays untested. Its image (`linuxserver/rdesktop`) is deprecated and no longer updated; it is on the dev stack's private network only. If you set up dev mode before this target existed, add it in the admin site with those values.

What dev mode swaps:
- **Certificates:** a private CA and certificate generated by `init` (valid 30 days) instead of Let's Encrypt. The key is world-readable inside the generated folder.
- **Identity:** a [Dex](https://dexidp.io) container with its mock connector, which signs in as a fixed user with no password.
- **Exposure:** ports are bound to 127.0.0.1 only. `init` refuses any domain that does not end in `.localhost`.

Never use dev mode on a server or any machine others can reach. Needs Docker Compose 2.24 or later. Untested.

## Control panel (GUI)

`sallyport-gui.cmd` (Windows) or `python sallyport_gui.py` (anywhere with Python 3) opens a small control panel in your browser. It checks that Docker, Compose and Git are present, clones or updates the repository into a folder you choose, has forms for every setting in `sallyport.yaml` and an editor for the targets (three lists: systems, people and groups, and logins saying who may use which system with which credentials) (with a raw-YAML view for anything else), validates before saving, and has buttons to apply settings, apply targets, and start, stop or restart the stack. It uses the same code as the command line.

At startup, if the environment checks pass, it fetches the repository and compares the stack's container images with their registries (by digest, without downloading them). If either has changed it shows a banner with the new commits, the newer images and the steps an update involves (re-initialise, download images, recreate containers, reload targets), worked out from the files that changed. The single **Update** button does all of it. Recreating containers interrupts active sessions. The image check needs the `docker buildx` plugin and registry access; if it cannot run, the banner says so. The checks and folder sections collapse when everything is fine, and the Output panel stays collapsed at the bottom until you open it (it opens by itself when you start an action).

The Operate section has four groups: **Apply settings** (first install, and after changing Settings), **Apply targets** (after changing Targets), **Stack** (start, stop, restart, status, logs) and **Test**. The update, image and apply steps are untested against a live stack.

The Settings form has an Identity provider selector (generic OpenID Connect, Auth0 or Google). Choosing one shows only the fields it needs, the exact values to enter in that provider's dashboard (callback and logout URLs for your domain) and, for Auth0, a copyable login Action that adds a groups claim. The Auth0 and Google provider support is untested against real tenants.

Install once: Python 3.12 or later, Git, Docker Desktop, then `pip install -r requirements.txt` (the `.cmd` does this for you).

It listens on 127.0.0.1 only, but any web page open in your browser can send requests to localhost, so every request needs a random token (in the URL it prints), an exact `Host` header and, for changes, a matching `Origin` and a JSON body. It stops when you close the tab or press Quit. Use it on the machine itself; do not forward its port. Saving from the forms rewrites the YAML files, so hand-written comments in them are not kept. Untested on Windows.

## Windows (Docker Desktop)

The stack itself is plain Docker Compose, so it runs on Docker Desktop (WSL 2 backend). The helper script runs inside a container, so Python is not needed. Use `sallyport.cmd` wherever this README says `./sallyport`:

```bat
copy sallyport.example.yaml sallyport.yaml
sallyport.cmd init
docker compose up -d --build
sallyport.cmd migrate-db
```

Notes:
- `migrate-db`, `load-targets` and `export-targets` need the stack running, because it connects to the database over the stack's internal network.
- Ports 80 and 443 must be forwarded to the Windows host and allowed through its firewall for Let's Encrypt. A desktop or laptop that sleeps is a poor gateway; use an always-on machine.
- Windows file permissions do not protect `.env` or `sallyport.yaml` the way mode 0600 does on Linux. Keep them in a folder only administrators can read.
- Untested on Windows. Please report anything that breaks.

## What you configure

| File | Purpose |
|---|---|
| `sallyport.yaml` | domain, ACME email, IdP, who may log in (emails and/or group IDs), session lifetime |
| the admin site | systems, people, groups and logins: what users may connect to, and with which credentials. Stored in the database, not in a file |

Secrets for Pomerium and the database are generated by `./sallyport init` into `.env` (mode 0600) and kept on re-runs.

Each target gets safe defaults: file transfer, drive redirection and printing are off, one session per user, NLA for RDP, certificate checking on. Clipboard is on by default and can be restricted per target. 

### Who can log in

`access.emails`, `access.groups` and `access.domains` are matched by Pomerium, which decides who may log in at all. They are alternatives: any one admits the person. If you list none, **anyone your identity provider authenticates is admitted**. That is reasonable when the provider's application for Sallyport only admits the people you intend (Auth0 does not do this by default; restrict the application with a login Action or Organizations), and the GUI shows an information note rather than a warning. Sallyport refuses it outright for providers that authenticate the public (Google, Microsoft `common`).

What each person then sees is set in the admin site, which has four lists. **Systems** are the machines. **Users** are people you give logins to or put in groups (optional). **Groups** are named lists of people, used to decide who sees a login. **Logins** say who may use which system: one `user`, a `group`, or `everyone`, with `username`/`password`/`private_key` saved or left out so that Guacamole asks the person at connect time. Each login becomes one connection named like `dc01 (alice@example.com)`, so `max_sessions` applies to each connection separately. Everyone admitted by the identity provider is created in Guacamole on first login and added to the `sallyport-users` group (by a database trigger), which sees only the `everyone` logins. A person with no login of their own therefore sees only those.

An `everyone` login **with saved credentials** hands those credentials to every current and future user: the GUI marks it with a warning and the admin site flags it. An `everyone` login with no saved credentials only shows the system, and gets an information icon. A group login with saved credentials is a shared account, so the target's own logs cannot tell the members apart; that gets an information note. IdP groups cannot be used to decide what people see, because Guacamole's header login receives only an email; groups here are lists of emails held in Sallyport. Accounts for named people are created ahead of their first login so permissions exist already. Emails are lower-cased and must match what the identity provider sends.

Revocation: removing someone from a login or group takes effect when you press Save and apply in the admin site, and does not end a session already open. If the identity provider alone decides who may log in, remove people there (disable the user or their role in Auth0); removing them from the admin site only removes their own logins and leaves them with the `everyone` logins. Sessions end at `session.lifetime`, or when you restart the stack. The older flat `targets:` list is still accepted and is shown converted in the GUI.

There is deliberately **no Guacamole administrator**: the default `guacadmin` account is deleted at first start. Targets are managed in the admin site.

### The admin site

`https://admin.<domain>` is a small separate service behind Pomerium, with its own allow-list (`admin.emails` / `admin.groups` in `sallyport.yaml`, set from the control panel). Only the Pomerium container is published; the admin service is on the internal network. The database is the source of truth, so no host access is needed to change targets. Saving rewrites the Guacamole connections and permissions in one transaction.

If a non-administrator opens the admin site, they see a short "administrators only" page that sends them back to the main site after a few seconds. Pomerium Core cannot customise its own 403 page (that is an Enterprise feature), so this works by letting everyone who may use Sallyport reach the admin route and having the admin service check the signed email against `admin.emails` itself. That applies when only `admin.emails` is set. If `admin.groups` is set, the service cannot evaluate groups, so Pomerium keeps enforcing the admin allow-list and non-administrators get Pomerium's plain 403.

How it is protected: every request must carry Pomerium's signed identity assertion, which the service verifies (signature, expiry, audience); browser-initiated writes must come from the admin origin with a custom header; saved passwords and keys are never sent back to the browser (fields show "saved" and can be replaced or removed); edits are version-checked so two admins cannot overwrite each other; every save is recorded in an audit log (what changed, never the credentials). It connects to the database as a role that can only touch the Guacamole connection tables and its own two tables. Be clear about the trade-off: **anyone who can open the admin site can add a login and grant it to themselves**, and the database holds credentials in plain text, as Guacamole's own configuration does. Keep `admin.emails` to the few people who administer the gateway, and use dedicated least-privilege accounts on the targets.

Guacamole shows a small Sallyport bar at the top right with an **Admin** link to this site (everyone sees it; people not on the allow-list are refused by Pomerium when they click). The bar is a Guacamole extension that `init` builds into `generated/sallyport-branding.jar`; it is hidden while a remote session is open. If the bar does not appear, check that Guacamole's logs mention loading the extension; this is the least-tested part of the stack.

`./sallyport migrate-db` creates the admin role and tables and, if the database is empty, imports `targets.yaml` if one exists. `./sallyport export-targets` writes the stored targets, credentials included, back to `targets.yaml` (a backup); `./sallyport load-targets` replaces what the database holds with that file, discarding admin-site edits. In dev mode `kilgore@kilgore.trout` is the admin.

## Known limitations (MVP)

Treat these as the to-do list, not as footnotes.

- **Audit trail is on the same box.** There is no session recording and no log forwarding. Guacamole's connection history lives in Postgres, and Pomerium and container logs live on the host, so anyone with host access can alter them. The tamper-resistant, client-owned logging we want comes first after the MVP.
- **Target credentials are stored in plain text** in Guacamole's database. Use dedicated, least-privilege service accounts, never personal ones. A vault integration is planned (Guacamole's official vault support is currently Keeper only; HashiCorp Vault support is scheduled for a later release).
- **No egress restriction.** `guacd` can reach whatever the host can. Restrict its traffic with host firewall rules (for example in the `DOCKER-USER` chain) so it can reach only the listed targets.
- **Group removal is not immediate.** Pomerium evaluates group claims at login; users removed from a group in the IdP keep access until their session ends. Keep `session.lifetime` short.
- **Floating `latest` image tags** (Postgres is pinned to major version 17 so an upgrade cannot corrupt its data directory). Pin versions and image digests before real use.
- **One server, one pre-auth surface.** Anything wrong in Pomerium or Envoy is reachable by the whole internet and is an emergency patch. Post-authentication bugs in Guacamole and `guacd` are less urgent but still matter if an engineer's session is stolen. Subscribe to the security announcements of all three.
- **Stolen sessions.** MFA protects the login, not the session cookie afterwards. Short lifetimes and the idle timeout limit the damage.
- **Not a full desktop replacement,** and file transfer is off. Engineers who need to move files will need another route.
- **The helper script and Compose file are untested against live containers.** See below.

## Upgrades

The database schema and setup scripts run only when the `postgres-data` volume is first created. To change them on an existing install, apply the SQL by hand. To update everything by hand: `./sallyport update` (see below). Plain `docker compose pull && docker compose up -d --build` also works, followed by `./sallyport migrate-db`. Back up the `postgres-data` volume first.

### No domain of your own: DuckDNS

If you have no DNS provider to hand, or a home or office connection whose public address changes, register a free name at duckdns.org and replace `domain:` in `sallyport.yaml` with:

```yaml
dynamic_dns:
  provider: duckdns
  subdomain: myfirm      # myfirm.duckdns.org
  token: your-duckdns-token
```

Sallyport then uses `myfirm.duckdns.org` as the domain and runs a small `duckdns` container that tells DuckDNS your current public address every five minutes. DuckDNS answers for every name under yours, so `authenticate.myfirm.duckdns.org` and `admin.myfirm.duckdns.org` need no records of their own. Everything else is unchanged: forward ports 80 and 443 to the machine (Let's Encrypt needs both), and Let's Encrypt certificates work because `duckdns.org` is on the public suffix list, so its rate limits apply per name. The token is stored in plain text in `sallyport.yaml` and `.env`. It will not work behind carrier-grade NAT (an ISP that shares one public address between customers), and the name stops working if you leave your DuckDNS account unused long enough for it to be reclaimed.

### Scheduled unattended updates

Certificate renewal does not depend on this: Pomerium's autocert renews Let's Encrypt certificates itself, keeping them in the `pomerium-data` volume, which updates never remove. It needs port 443 reachable from the internet and the container running, so a nightly update that leaves the stack healthy is also what keeps renewal working. Moving from `acme_staging: true` to real certificates is a one-off manual change.

Set `updates.schedule: "03:00"` (quoted, 24-hour, the server's local time) in `sallyport.yaml` and run `./sallyport schedule apply` (the control panel does this when you apply settings). It installs a daily job running `./sallyport update --unattended`: fetch the latest code, pull the images, rebuild the admin image, recreate what changed, migrate the database, then check every container is running and healthy. If not, it resets the code to the previous commit, re-tags the previous images, recreates the stack and records the outcome in `generated/update-status.json` and `generated/update.log`. Remove the schedule by emptying the setting and applying again, or `./sallyport schedule remove`.

**Critical updates.** The schedule is the normal path, but the daily job is backed by an hourly check (on by default; turn it off with `updates.critical: false`). Each hour it fetches the repository without changing anything and looks for a file named `CRITICAL_UPDATE.json` on the upstream branch. If that file carries an `id` this install has not yet applied, it runs the full update immediately, whatever the time and whether or not anyone is connected, so sessions in progress end. The file is meant for rare cases such as a pre-authentication weakness in Pomerium, and looks like `{"id": "2026-12-01-pomerium", "summary": "why"}`; only `id` is read. A critical update that fails and is rolled back is not retried for six hours, and the outcome is in `generated/update-status.json`. Anyone who can push to the tracked branch can already ship anything, so the flag changes only when an update lands, not who can send one.

Know what you are accepting. The trade-off is deliberate: a gateway on the internet that nobody patches is the likelier failure for a small business than a poisoned upstream, and anyone who is paying attention to the supply chain can pin versions (below). An unattended update runs **whatever the repository's `main` branch and the floating image tags (`latest`) contain at 03:00**; a bad or malicious upstream change reaches the server without anyone looking, and a short outage at update time ends sessions in progress. Rollback is best effort (it cannot undo a database migration). Consider pinning image versions in `compose.yaml` and tracking a branch you control. On Linux as root it installs a systemd timer; as a normal user, a crontab entry. On Windows it uses Task Scheduler, which only runs while you are signed in and Docker Desktop is running, so for real unattended use run Sallyport on a Linux server.

## Optional hardening

`compose.hardening.yaml` drops capabilities and makes filesystems read-only. It is untested and may need relaxing per service:

```sh
docker compose -f compose.yaml -f compose.hardening.yaml up -d
```
